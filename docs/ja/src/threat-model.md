# 脅威モデル

**対象範囲。** aaai は「信頼しないことが前提のフォルダ」を読み取り、「第三者
に共有するためのファイル」を書き出します。aaai のセキュリティ上の立ち位置は
この一文に尽きます。本書は、何を守るのか、信頼境界はどこか、何を防御し、そ
して — 同じく重要なこととして — 何を防御しないのかを明示します。

**想定読者。** メンテナ、レビュア、および重要なデータに対して aaai を使う前に
評価を行う方。

**最終レビュー:** 2026-10-20、`0.42.0` および未リリース分に対して。

**新しいデータフロー、外部連携、認証・認可ロジックを導入するリリースでは、本

主張になります。

## 1. 守るべき資産

| 資産 | 性質 | 重要な理由 |
|---|---|---|
| 監査対象フォルダの内容 | 機密性 | 顧客のリリース成果物や本番設定である可能性がある。aaai はこれを読み、要約を別の場所に書き出す |
| 監査記録 — 理由・戦略・承認 | 完全性 | 本製品の価値は、半年後に記録された理由が信頼できることにある。密かに書き換えられた理由は、理由が無いことより悪い |
| 選択した 2 つのフォルダの外側すべて | 機密性・完全性 | 利用者が指定したのは 2 つのフォルダである。ディスク上のそれ以外は、読み取りも書き込みも範囲外 |
| 利用者の設定 | 完全性、限定的な機密性 | `profiles.yaml` はファイルパスを保持し、通常そこにはアカウント名が含まれる |
| 出力したレポート | 出力先での機密性 | その場にいなかった人に送るために存在する |

## 2. 信頼境界

**B1 — フォルダの内容は信頼しない。** 中心となる境界。aaai が想定する用途で
は、「変更後」フォルダは出所そのものが監査対象の成果物です。ファイル名、ディ
レクトリ構造、ファイル内容、リンク先、ファイルサイズはすべて、その生成者の影
響下にあります。

**B2 — 監査定義ファイルは準信頼。** 通常は GUI を通じて利用者自身が書きます
が、コミットして共有されることを前提とした YAML ファイルであるため、管理外の
リポジトリから届くことがあります。正規表現と期待内容を含みます。

**B3 — レポートの出力先は境界の外。** 利用者が選んだパスに書き出され、他者
が、場合によっては機械が読みます。

**B4 — 依存グラフ。** 570 クレート。いずれも自前ではありません。

## 3. aaai が防御しないもの — および、なぜ攻撃面が存在しないのか

過大に受け取られないよう、明示します。

**ネットワーク経由の攻撃者は存在しない。ネットワークコードが無いため。**
aaai には HTTP クライアント、ソケットコード、テレメトリ、更新確認、クラッシュ
レポートのいずれもありません。検証可能です — `Cargo.lock` に HTTP クライアン
トクレートは現れず、ソースにソケット型は現れません。コードベース中の 2 つの
URL は SARIF レポートに文字列として書き出されるスキーマ識別子とリポジトリリン
クであり、取得されることはありません。

**権限昇格は存在しない。権限が無いため。** aaai は、起動した利用者の権限で動
作する単一利用者向けのデスクトップおよびコマンドラインツールです。認証、認可、
マルチテナント、常駐プロセスのいずれもありません。

**常駐サービスは無い。** 待ち受けるものは無く、実行と実行の間に動くものもあり
ません。

**敵対的な操作者に対する防御は無い。** 利用者がフォルダを指定し、偽の理由を付
けて変更を承認すれば、aaai はその理由をそのまま記録します。aaai が検証するの
は理由が「存在すること」であって、「真実であること」ではありません。

**アクセシビリティツリー連携は無い。** セキュリティとは無関係ですが、質問が多
いため明記します。GUI は AccessKit / AT-SPI / UIA のいずれも提供しません。スク
リーンリーダー利用者には CLI を推奨します。

## 4. 脅威

各対策には、それを閉じた RFC と、それを支えるテストまたは証跡の両方を示しま
す。参照先の無い対策は、対策ではなく主張です。

| # | 脅威 | 境界 | 状態 | 根拠 |
|---|---|---|---|---|
| **T1** | 選択フォルダ内のリンクが外部を指し、ディスク上の別の場所の内容が差分やレポートに混入する | B1 | **対策済** | RFC 098。`selected_root_symlink_is_rejected`、`symlinked_file_is_incomparable_and_outside_content_is_absent`、`symlinked_directory_is_not_traversed`、`broken_and_cyclic_links_are_reported_without_following`、`relative_inside_links_and_link_type_conflicts_are_incomparable`、および Windows リパースポイント版 — `crates/aaai/src/diff/tests.rs`。敵対的マトリクスは 3 プラットフォームすべてで実施済 |
| **T2** | `reason` / `ticket` / `note` 中の秘密情報が共有レポートに出る | B3 | **対策済** | RFC 103 (エンジン・CLI)、RFC 104 (GUI)。`connection_string_password_masked`、`bearer_token_masked`、`multiple_secrets_all_masked` (`masking/tests.rs` ほかプロパティテスト)、`markdown_export_does_not_contain_the_secret`、`json_export_does_not_contain_the_secret`、`gui_export_matches_cli_report_for_the_same_input` (`aaai-gui/src/app/update/save/tests.rs`) |
| **T3** | ファイル名や差分行中の悪意ある内容が、レポートを開いた側で解釈される — 表計算の数式インジェクション、HTML / SARIF のエスケープ漏れ | B1 → B3 | **対策済** | RFC 103。`every_surface_encodes_and_masks_every_untrusted_field` — `crates/aaai/src/report/generator/tests.rs` |
| **T4** | 定義ファイル中の病的な正規表現が監査を停止させる | B2 | **表現不可能** | `regex` クレートは有限オートマトン方式であり、線形時間・バックトラッキング無し。これは依存選択の性質であり、その選択が変われば失われるため記録する |
| **T5** | 監査対象フォルダ内の巨大ファイルがメモリを枯渇させる | B1 | **未対策 — 予定済** | §5 |
| **T6** | aaai が監査対象フォルダを変更してしまう | B1 | **対策済** | 入力は読み取り専用で開く。`link_audit_preserves_namespace_content_and_stable_metadata` と Windows 版が、実行前後のサイズ・モード・デバイス・inode・mtime を取得して一致を検証する。**範囲に関する注記:** これらが覆うのはリスクが最も高いリンク監査経路であり、「いかなる経路も書き込まない」ことの全面的な証明ではない |
| **T7** | 脆弱または汚染された依存 | B4 | **部分的に対策済** | `cargo audit` を CI で実行し、**脆弱性は 0 件**。情報レベルの警告 8 件を受容 — §6 |
| **T7a** | `unsafe-libyaml` が監査定義ファイルを解析し、unsafe Rust であり、かつ保守終了 | B2 | **受容、個別に記録** | §6.1 |
| **T8** | aaai 自身のコードにおけるメモリ安全性の欠陥 | 全体 | **対策済** | プロジェクトコードに `unsafe` は一切無い — `crates/` の grep で検証可能 |
| **T9** | 共有したレポートが実際に秘匿処理されたか利用者が判別できない | B3 | **受容する制約** | §5 |

## 5. 既知のギャップ

### T5 — ファイル読み込みに上限が無い (予定済)

`read_file` はファイル全体を `Vec<u8>` として返し、サイズ上限がありません。そ
のため両ツリーのすべてのファイルが、ハッシュ化や分類の前に丸ごとメモリに読み
込まれます。`LARGE_FILE_THRESHOLD` (1 MB) はガードではありません — 唯一の用途
は **Exact** 戦略が大きなファイルに適用されたときの警告であり、しかも読み込み
の後です。

**帰結。** ディスクイメージ、コアダンプ、ローテートされていないログなど、単一
の巨大ファイルがメモリを枯渇させ得ます。並列比較により複数が同時に常駐するこ
ともあります。結果は、利用者が対処できるエラーではなく OOM による異常終了です。

**深刻度: 中、可用性のみ。** 情報漏洩も破壊も起きません。利用者自身がそのファ
イルを指定することが前提です。

**2 段階で予定済。** 読み込みに上限を設け「比較するには大きすぎる」結果を返す
部分はリリースユニット 4 に承認済。巨大ファイルを有界メモリで比較可能に保つス
トリーミングハッシュ化は、スケーラブル差分のマイルストーンに属します。
`ROADMAP.md` を参照。

### T9 — 秘匿処理が無言である (受容)

秘匿処理は無条件に適用されますが、実際に何かが秘匿されたかどうかを aaai は伝
えられません — 秘匿 API がパターン一致の有無を返さないためです。したがって
「秘密情報が無かった」と「秘密情報を除去した」は見分けがつきません。

**意図的に受容。** 伝えるには秘匿 API に新しい信号が必要です。ここに記録するの
は、*「安全だと思い込んだ」* が単なる使い勝手ではなくセキュリティ上の結果だか
らです。

## 6. 受容した依存アドバイザリ

ゲート C0 は、依存監査がクリーンであるか、例外が正式に受容されていることを要
求します。`cargo audit` の報告は **脆弱性 0 件**。以下 8 件の情報レベル警告を、
到達性とともに記録のうえ受容します。

| アドバイザリ | クレート | 種別 | 到達性と理由 |
|---|---|---|---|
| `RUSTSEC-2024-0449` | `unsafe-libyaml` | 保守終了 | **§6.1 — 個別に記録** |
| `RUSTSEC-2026-0253` | `lru` | 健全性 | 実行時。`cryoglyph` → `iced_wgpu` → `iced` 経由。`LruCache::pop()` の use-after-free は、格納キーの `Drop` がパニックし巻き戻しが有効な場合にのみ到達。**自力では修正不可** — `cryoglyph` が `lru` を修正版 0.18.2 未満に固定しており、引き上げるリリースが無い |
| `RUSTSEC-2024-0436` | `paste` | 保守終了 | ビルド時の手続きマクロのみ。実行時には存在しない |
| `RUSTSEC-2026-0206` | `rustybuzz` | 保守終了 | 実行時。`iced` 経由のテキストシェーピング。上流が変わらない限り代替不可 |
| `RUSTSEC-2026-0192` | `ttf-parser` | 保守終了 | 実行時。`iced` 経由のフォント解析。同上 |
| `RUSTSEC-2026-0371` | `zbus_names` | 保守終了 | 2026-10-16 に上流で `zbus` 6.0.0 へ統合。`iced` → `winit` 経由。コードに問題があるのではなく、クレートが移動した |
| `RUSTSEC-2026-0370` | `zvariant` | 保守終了 | 同じ経緯 |
| `RUSTSEC-2026-0372` | `zvariant_derive` | 保守終了 | 同じ経緯 |

**最初の 2 件を除き、`iced` が自身の依存を更新した時点で解消します。** aaai が
修正すべきものではなく、追いかけずに記録します。

### 6.1 `unsafe-libyaml` — 性質が異なる 1 件

```
unsafe-libyaml 0.2.11
└── serde_yaml 0.9.34+deprecated
    ├── aaai  (エンジン、直接依存)
    └── rust-i18n-macro  (ビルド時)
```

次の 3 点が重なることで、他と性質が異なります。

- **unsafe Rust** である — アドバイザリは「libyaml の C コードを機械的に
  unsafe Rust へ翻訳したもの」と記述している
- **`serde_yaml` (これ自体が非推奨)** を経由し、エンジンの直接依存である
- **監査定義ファイル** を解析する。これは §2 が **B2 — 準信頼** に分類する入力

つまり、名前の付いた信頼境界の上に位置する唯一の保守終了依存であり、しかもメ
モリ安全でないコードで、アドバイザリ自身が「バグは上流で修正されない」と述べ
ています。

**脆弱性ではありません。** CVE も既知の悪用も無く、プロジェクト開始時から存在
します。**その前提で受容** し、フォントクレート 3 件や名称変更された D-Bus ヘ
ルパと同等に読まれないよう個別に記録します。

**本当の解決は `serde_yaml` からの移行** であり、未予定です。永続化される監査
定義・設定・プロファイルの各形式に触れるため、依存の差し替えではなく互換性の
変更であり、独自の設計を要します。

<https://github.com/nabbisen/aaai/issues> に issue を作成してください。上記の
